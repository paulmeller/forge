description: Deploy Forge to Google Cloud Run with Turso, Cloud Scheduler, and Secret Manager.

Forge is designed to run as a single small Cloud Run service against a remote libSQL database, with no durable-execution vendor dependency. This guide walks through a production deployment.

## Architecture overview

```
┌─────────────────┐     HTTPS, OIDC auth      ┌──────────────────┐
│  Cloud Scheduler │─────────────────────────▸ │                  │
│  (every 60s)     │        POST /api/tick     │    forge-web     │
└─────────────────┘                            │    Cloud Run     │
                                                │    Next.js       │
┌─────────────────┐          HTTPS             │  (Console, API,  │
│  Users / GitHub  │─────────────────────────▸ │   webhooks,      │
│  webhooks        │                           │   tick engine)   │
└─────────────────┘                            └────────┬─────────┘
                                                         │
                                                         ▼
                                                ┌──────────────────┐
                                                │  Turso (libSQL)   │
                                                │  remote database  │
                                                └──────────────────┘
```

- **forge-web** — Next.js (App Router). Hosts the Console, the REST API, the webhook receiver, and the tick engine (`apps/web/src/server/tick/`, orchestrated by `runTick()`). Autoscales, scale-to-zero allowed.
- **`POST /api/tick`** — a route on `forge-web`, invoked by Cloud Scheduler every 60 seconds. Runs one tick of work (claim Tasks, poll sessions, run Gate, check budgets) in-process and returns.
- **Turso** — remote libSQL database over HTTP. `forge-web` connects to it.

## Prerequisites

- [Google Cloud CLI](https://cloud.google.com/sdk/docs/install) (`gcloud`)
- A GCP project with Cloud Run, Cloud Scheduler, and Secret Manager APIs enabled
- A [Turso](https://turso.tech) account and database
- Docker (for building images locally, or use Cloud Build)

## 1. Create the Turso database

```bash
turso db create forge-prod
turso db tokens create forge-prod
```

Save the connection URL and auth token. You'll need them for environment variables.

Run migrations against the production database:

```bash
DATABASE_URL="libsql://forge-prod-<your-org>.turso.io" \
DATABASE_AUTH_TOKEN="<your-token>" \
pnpm --filter @forge/db db:migrate
```

## 2. Build the Docker image

Forge ships a single Dockerfile at `apps/web/Dockerfile`. The web app uses Next.js standalone output mode (`output: 'standalone'` in `next.config.ts`), which produces a minimal self-contained Node.js server.

### forge-web

```bash
docker build -t gcr.io/$PROJECT_ID/forge-web -f apps/web/Dockerfile .
docker push gcr.io/$PROJECT_ID/forge-web
```

The Dockerfile uses a multi-stage build:

1. **deps** — installs dependencies with pnpm (frozen lockfile).
2. **builder** — runs `pnpm --filter @forge/web build`, producing the standalone output.
3. **runner** — copies the standalone output (`server.js`, static assets, public files) plus the repo-root `skills/` directory (synced into the DB at boot via `instrumentation.ts`, overridable with `FORGE_SKILLS_DIR`). Runs as a non-root user on port 3000.

There is no separate tick image — the tick engine ships inside this same image and runs in-process when Cloud Scheduler hits `/api/tick`.

## 3. Store secrets

Use Google Secret Manager for sensitive values:

```bash
echo -n "sk-ant-..." | gcloud secrets create ANTHROPIC_API_KEY --data-file=-
echo -n "libsql://forge-prod-xxx.turso.io" | gcloud secrets create DATABASE_URL --data-file=-
echo -n "<turso-token>" | gcloud secrets create DATABASE_AUTH_TOKEN --data-file=-
echo -n "<random-32-chars>" | gcloud secrets create BETTER_AUTH_SECRET --data-file=-
echo -n "<github-token>" | gcloud secrets create GITHUB_APP_TOKEN --data-file=-
```

## 4. Deploy forge-web

There's one deploy for the whole app — the Console, API, webhooks, and the tick engine all ship in this one image. `forge-web` stays `--allow-unauthenticated` at the Cloud Run layer (the Console and webhooks need public access); `/api/tick` protects itself with an app-level OIDC check against `TICK_EXPECTED_AUDIENCE`.

```bash
gcloud run deploy forge-web \
  --image gcr.io/$PROJECT_ID/forge-web \
  --region $REGION \
  --platform managed \
  --allow-unauthenticated \
  --port 3000 \
  --set-secrets="DATABASE_URL=DATABASE_URL:latest,\
DATABASE_AUTH_TOKEN=DATABASE_AUTH_TOKEN:latest,\
BETTER_AUTH_SECRET=BETTER_AUTH_SECRET:latest,\
ANTHROPIC_API_KEY=ANTHROPIC_API_KEY:latest,\
GITHUB_APP_TOKEN=GITHUB_APP_TOKEN:latest" \
  --set-env-vars="BETTER_AUTH_URL=https://forge-web-xxx.a.run.app,\
FORGE_BACKEND=managed-agents,\
TICK_EXPECTED_AUDIENCE=https://forge-web-xxx.a.run.app,\
TICK_EXPECTED_ISSUER_EMAIL=scheduler@$PROJECT_ID.iam.gserviceaccount.com"
```

Replace `BETTER_AUTH_URL` and `TICK_EXPECTED_AUDIENCE` with the actual Cloud Run service URL after the first deploy. You may need to update and redeploy.

### Optional env vars for forge-web

| Variable | Purpose | Default |
|---|---|---|
| `GATEWAY_URL` | Required if `FORGE_BACKEND=gateway`. URL of your AgentStep Gateway. | _(none)_ |
| `GATEWAY_API_KEY` | API key for the gateway. Required when using `gateway` backend. | _(none)_ |
| `GITHUB_WEBHOOK_SECRET` | Enables GitHub webhook dispatch (issue comment and CI-fix triggers). | _(none)_ |
| `FORGE_DEFAULT_AGENT_ID` | Agent ID used by GitHub-dispatched missions. | _(none)_ |
| `FORGE_DEFAULT_GITHUB_VAULT_ID` | GitHub MCP vault ID for GitHub-dispatched missions. | _(none)_ |
| `FORGE_MA_ENVIRONMENT_ID` | Managed Agents environment ID. Required when using `managed-agents` backend. | _(none)_ |
| `TASK_RETRY_MAX` | Maximum CI-failure retries before a Task is marked `failed`. | `3` |
| `TICK_EXPECTED_AUDIENCE` | Cloud Run service URL, used to verify OIDC tokens from Cloud Scheduler on `/api/tick`. | _(required in production)_ |
| `TICK_EXPECTED_ISSUER_EMAIL` | Service account email that Cloud Scheduler uses. Optional but adds a second layer of defense. | _(none)_ |
| `FORGE_SKILLS_DIR` | Overrides the path the skills library is synced from at boot. The Docker image sets this to `/app/skills`. | `skills/` at repo root |

## 5. Set up Cloud Scheduler

Create a Cloud Scheduler job that POSTs to `forge-web`'s `/api/tick` route every 60 seconds:

```bash
# Create a service account for the scheduler
gcloud iam service-accounts create forge-scheduler \
  --display-name "Forge Tick Scheduler"

# (Optional, defense-in-depth) grant it invoker on forge-web, since
# forge-web is --allow-unauthenticated at the Cloud Run layer already
gcloud run services add-iam-policy-binding forge-web \
  --region $REGION \
  --member "serviceAccount:forge-scheduler@$PROJECT_ID.iam.gserviceaccount.com" \
  --role "roles/run.invoker"

# Create the scheduler job
gcloud scheduler jobs create http forge-tick \
  --location $REGION \
  --schedule "* * * * *" \
  --http-method POST \
  --uri "https://forge-web-xxx.a.run.app/api/tick" \
  --oidc-service-account-email "forge-scheduler@$PROJECT_ID.iam.gserviceaccount.com" \
  --oidc-token-audience "https://forge-web-xxx.a.run.app"
```

The scheduler sends an OIDC token with each request. The `/api/tick` route verifies the token against `TICK_EXPECTED_AUDIENCE` (and, if set, `TICK_EXPECTED_ISSUER_EMAIL`) before executing.

### Sub-minute cadence

If you need sub-minute tick cadence in the future, flip `forge-web` to `--min-instances=1` and run `runTick()` on an in-process interval instead of per-request. No architectural changes are needed — the same code path works either way.

## 6. Verify the deployment

```bash
# Health check
curl https://forge-web-xxx.a.run.app/api/health
# Expected: {"status":"ok","service":"forge-web"}

# Trigger a tick manually
curl -X POST https://forge-web-xxx.a.run.app/api/tick \
  -H "Authorization: Bearer $(gcloud auth print-identity-token)"
```

Open the Console URL in your browser and create a test Mission.

## Environment variable summary

| Variable | Required for | Description |
|---|---|---|
| `DATABASE_URL` | always | Turso connection string |
| `DATABASE_AUTH_TOKEN` | always | Turso auth token |
| `BETTER_AUTH_SECRET` | always | Session signing secret |
| `BETTER_AUTH_URL` | always | Public URL of forge-web |
| `FORGE_BACKEND` | always | `managed-agents` or `gateway` |
| `ANTHROPIC_API_KEY` | `managed-agents` backend | Anthropic API key |
| `FORGE_MA_ENVIRONMENT_ID` | `managed-agents` backend | Managed Agents environment ID |
| `GATEWAY_URL` | `gateway` backend | AgentStep Gateway URL |
| `GATEWAY_API_KEY` | `gateway` backend | AgentStep Gateway API key |
| `GITHUB_APP_TOKEN` | always | For repo cloning and Checks API polling |
| `TICK_EXPECTED_AUDIENCE` | recommended | OIDC audience verification for `/api/tick` |
| `TICK_EXPECTED_ISSUER_EMAIL` | optional | OIDC issuer verification for `/api/tick` |
| `TICK_ALLOW_UNAUTHENTICATED` | local dev only | Bypasses OIDC verification for curl testing — never set in production |
| `FORGE_SKILLS_DIR` | optional | Overrides the on-disk skills library path synced at boot |

## Deploying updates

On merge to `main`, rebuild and redeploy the image:

```bash
docker build -t gcr.io/$PROJECT_ID/forge-web -f apps/web/Dockerfile .
docker push gcr.io/$PROJECT_ID/forge-web

gcloud run deploy forge-web --image gcr.io/$PROJECT_ID/forge-web --region $REGION
```

Cloud Run performs zero-downtime rolling deploys. The Ledger's append-only design means no data is lost across deploys. `.github/workflows/deploy.yml` runs this same build-push-deploy sequence for `forge-web` on merge to `main`.

## Alternative platforms

While Cloud Run is the reference deployment target, the same Docker image runs on any container platform:

- **Fly.io** — deploy the app, use a cron trigger (or Fly's built-in scheduled machines) to hit `/api/tick`.
- **Railway** — deploy from the repo, configure a cron job to hit `/api/tick`.
- **Kubernetes** — deploy as a Deployment with a CronJob that curls `/api/tick`.
- **Embedded libSQL** — for local or single-machine deployments, use `file:./forge.db` instead of Turso. No remote database needed.
